# Архітектура оптимізації продуктивності WheelDecalsHub

> **Для збереження досягнутих показників PageSpeed Insights і стабільності Core Web Vitals будь-яка нова функціональність, OCMOD-модифікатор, зміна CSS або JavaScript, шаблонів, зображень, шрифтів чи серверного кешування повинна вбудовуватися в існуючу performance-архітектуру WheelDecalsHub, а не обходити її локальними латками.**

## 1. Мета документа

Цей документ описує **інженерні принципи, інваріанти продуктивності та поточну архітектуру оптимізації WheelDecalsHub**.

Документ призначений для тих, хто буде вносити зміни до структури, модулів, стилів, скриптів, зображень, доповнень або налаштувань сайту. Його мета — дати достатньо контексту, щоб:

- розуміти, **яку логіку продуктивності потрібно зберігати**;
- не повертати випадково вже усунені вузькі місця;
- вбудовувати нові доробки в наявні WDH-шари;
- відрізняти архітектурний контракт від випадкової поточної реалізації;
- безпечно змінювати CSS, JavaScript, OCMOD, доставку зображень, шрифти та серверне кешування;
- перевіряти не лише функціональність, а й відсутність регресій LCP / CLS / TBT.

Мова постійної документації проєкту — українська. Імена файлів, шляхів, класів, функцій, селекторів, атрибутів і фрагментів коду залишаються без перекладу.

## 2. Загальні принципи оптимізації продуктивності

### 2.1. Оптимізується конкретний тип сторінки, а не «сайт взагалі»

Головна сторінка, категорія і картка товару можуть використовувати ті самі ресурси, але мати різні причини поганого LCP, CLS або блокування відображення.

Тому рішення оцінюються окремо для:

- головної сторінки;
- категорії;
- картки товару;
- мобільної версії;
- desktop/tablet.

Спочатку стабілізується конкретний тип сторінки, і лише потім рішення за потреби узагальнюється на інші сторінки.

### 2.2. Спочатку визначається реальна причина метрики, потім змінюється код

Погана оцінка PSI сама по собі не є діагнозом.

Перед зміною потрібно встановити:

- який саме елемент є LCP;
- коли він з'являється у DOM;
- коли браузер виявляє його ресурс;
- коли починається мережевий запит;
- який природний і фактичний розмір ресурсу;
- чи блокується його відображення CSS або JavaScript;
- який саме DOM-вузол створює зміщення макета;
- яка залежність або порядок виконання коду реально викликає проблему.

Принцип проєкту:

```text
вимірювання
→ доведена причина
→ мінімальна зміна
→ повторна перевірка
```

### 2.3. Перший екран сторінки сайту має бути максимально самодостатнім

Браузер повинен якомога раніше отримати все, що справді необхідно для завершеного першого екрана:

```text
правильний початковий DOM
+ мінімальний критичний CSS
+ стабільна геометрія
+ критичні дані про шрифти
+ пріоритетний LCP-ресурс
```

Усе, що першому екрану не потрібне, не повинно без необхідності конкурувати з критичним шляхом відображення.

### 2.4. Критичний CSS має бути справді критичним

**Критичний CSS** — це мінімальний набір стилів, необхідний для правильного першого відображення сторінки сайту: формування геометрії першого екрана, запобігання CLS і коректного показу ключового вмісту до завантаження решти стилів.

Усе, що не потрібне для першого відображення сторінки сайту, за можливості має залишатися поза критичним шляхом завантаження.

Мета критичного CSS — не просто «перенести CSS inline».

У критичному шарі повинні залишатися лише правила, без яких перший екран:

- має неправильне розташування;
- змінює розміри після першого відображення;
- виглядає структурно зламаним;
- створює CLS;
- не може коректно показати LCP.

Стилі нижньої частини сторінки, popup, форм, zoom, carousel та інших некритичних компонентів не повинні блокувати перше відображення лише тому, що історично лежали у `<head>`.

### 2.5. Відкладені ресурси не повинні створювати CLS, FOUC або функціональні регресії

Винести stylesheet або script з критичного шляху недостатньо.

Після defer потрібно перевірити:

```text
що змінилося під час першого відображення
→ яка геометрія стала нестабільною
→ який мінімальний набір правил треба повернути в критичний CSS
→ чи залишилися CLS / FOUC / race conditions
```

**Defer не є самоціллю.** Якщо defer конкретної залежності порушує порядок виконання, архітектура повинна враховувати код, який від неї залежить.

### 2.6. LCP — це шлях доставки ресурсу, а не лише його вага

Для LCP-зображення оцінюється весь шлях:

```text
HTML виявляє ресурс
→ браузер призначає йому пріоритет
→ сервер віддає ресурс потрібного фізичного розміру та формату
→ CSS уже задає кінцеву геометрію
→ елемент може бути відображений одразу
```

Практичні складові:

- адекватний фізичний розмір;
- WebP або інший доречний сучасний формат;
- раннє виявлення;
- `fetchpriority="high"` там, де це виправдано;
- відсутність lazy-load для LCP;
- відсутність JavaScript-залежності для появи LCP;
- відсутність зайвої конкуренції з блокувальними ресурсами.

### 2.7. Не передавати браузеру зайві пікселі

Розмір переданого зображення має бути близьким до фактичного розміру відображення з розумним запасом під щільність екрана.

Для адаптивних сценаріїв перевага надається `srcset` і `<picture>`, якщо це дає браузеру змогу вибрати доречний ресурс.

### 2.8. CLS лікується стабільною геометрією, а не маскуванням симптомів

Потрібно визначити, яка саме коробка змінила розмір або положення і чому браузер не знав її кінцевої геометрії до першого відображення.

Основні інструменти:

- `width` / `height`;
- `aspect-ratio`;
- стабільні розміри контейнера;
- критичний CSS;
- правильний порядок DOM;
- відсутність пізніх вставок і переміщень.

Якщо кінцева структура DOM відома серверу, її потрібно віддати правильно одразу, а не перебудовувати після першого відображення через JavaScript.

### 2.9. JavaScript першого екрана має бути мінімальним

Особливо уважно слід ставитися до:

- jQuery;
- slider/carousel;
- popup;
- zoom;
- reviews;
- upload;
- datetime picker;
- сторонніх віджетів.

Якщо код не потрібний для першого відображення або LCP, він не повинен без необхідності затримувати їх.

### 2.10. Залежність оптимізується разом із кодом, що від неї залежить

Наприклад, просто додати `defer` до jQuery недостатньо, якщо нижче є inline-код, який виконується під час розбору HTML.

Правильна модель:

```text
ресурс
+ код, що від нього залежить
+ порядок виконання
```

Оптимізується весь ланцюжок, а не окремий `<script>`.

### 2.11. Шрифти — такий самий ресурс першого екрана, як CSS і зображення

Для першого екрана важливі:

- локальне зберігання;
- WOFF2;
- коректний `font-display`;
- preload лише реально потрібного шрифту;
- правильний URL;
- відсутність помилкових або дубльованих запитів;
- раннє оголошення `@font-face`.

Сам по собі preload нічого не гарантує — фактичний результат перевіряється через Network і Performance.

### 2.12. Не «дооптимізовувати» вже стабільний зелений вузол без доведеної причини

Якщо LCP хороший, CLS стабільний, TBT відсутній або мінімальний, Console без помилок і реальної проблеми не видно, наступна «оптимізація» може дати більше ризику, ніж користі.

Це особливо важливо для складних застарілих механізмів на кшталт zoom, slider і ланцюжків JavaScript-залежностей.

### 2.13. PSI — індикатор, а браузерна діагностика пояснює причину

Для діагностики використовуються разом:

- PageSpeed Insights;
- панель Performance;
- каскад завантаження Network;
- геометрія DOM;
- PerformanceObserver;
- Resource Timing;
- природні та фактичні розміри зображень;
- час завантаження шрифтів;
- Console.

Один запуск PSI не є достатнім доказом регресії або покращення. Важлива повторювана картина.

### 2.14. HTML та inline-код також мають ціну

Критичний CSS, base64-шрифти та inline JavaScript можуть зменшити кількість окремих запитів, але збільшують початковий HTML і час його завантаження та розбору.

Inline має сенс лише тоді, коли виграш від відсутності окремого запиту перевищує ціну збільшення початкового документа.

### 2.15. Кешування — частина архітектури продуктивності

У проєкті необхідно розрізняти:

```text
вихідний код
→ згенерований OCMOD-код
→ робочий кеш застосунку
→ кеш Twig
→ фактичний HTML
→ HTTP-заголовки кешування
→ кеш браузера
```

Застарілий кеш не повинен автоматично трактуватися як помилка нового коду.

### 2.16. Локальне виправлення PSI не повинно руйнувати загальну систему

Не можна покращувати один симптом ціною повернення кількох старих вузьких місць.

Хороше виправлення повинно одночасно:

- вирішувати доведену причину;
- зберігати функціональність;
- не повертати старі регресії;
- залишатися підтримуваним у майбутньому.

### 2.17. Оптимізація повинна перетворюватися на архітектуру, а не на набір латок

Кінцева мета — не набір випадкових preload, timers, inline styles та OCMOD-латок, а системні шари:

- єдина архітектура критичного CSS;
- відображення з урахуванням маршруту і типу пристрою;
- правильний DOM, сформований на сервері;
- контрольоване відкладене завантаження ресурсів;
- контрольована доставка зображень;
- локальна доставка шрифтів;
- узгоджені правила кешування.

Коротко:

> **Дати браузеру якомога раніше мінімальний завершений перший екран. Не змушувати його завантажувати або виконувати те, що цьому екрану не потрібно. Не змінювати геометрію після першого відображення. Пріоритезувати реальний LCP-ресурс. Усе інше переносити за межі критичного шляху лише після перевірки, що це не створює FOUC, CLS, race conditions або функціональних регресій.**

## 3. Принципи для нових доробок

> **Головне правило:** нова функціональність повинна вбудовуватися в архітектуру продуктивності WheelDecalsHub, а не вимагати її демонтажу.

Будь-яка нова доробка повинна використовувати наявні механізми проєкту й не обходити їх локальними латками.

Для будь-якої нової доробки діють такі правила:

- новий CSS не повинен автоматично ставати блокувальним для відображення;
- новий JavaScript не повинен вимагати повернення синхронного jQuery без доведеної необхідності;
- нові елементи першого екрана повинні мати стабільну геометрію до першого відображення;
- нові зображення повинні отримувати розмір, формат і стратегію завантаження відповідно до своєї ролі;
- структурні відмінності mobile/desktop за можливості формуються на сервері;
- новий критичний CSS для конкретного маршруту підключається через наявну WDH-архітектуру;
- не створюється друге джерело істини для критичного CSS;
- наявні WDH OCMOD/library-шари не обходяться прямими латками;
- після доробки перевіряється не лише нова функція, а й уже стабільні LCP / CLS / TBT;
- стабільний зелений тип сторінки не змінюється «заодно» без окремої причини.

## 4. Інваріанти продуктивності

Інваріант продуктивності — це умова, яка вважається частиною архітектурного контракту. Її не можна порушувати як побічний ефект іншої задачі.

### 4.1. Глобальні інваріанти

- `critical-*.css` є єдиним джерелом істини для критичного CSS.
- `storage/modification` та робочі кеші не є джерелом постійних змін.
- Геометрія першого екрана повинна бути стабільною до першого відображення.
- Залежність змінюється лише разом із кодом, що від неї залежить, і з урахуванням порядку виконання.
- Логіка для маршруту або типу пристрою не дублюється паралельним механізмом без доведеної потреби.
- Нові оптимізації для конкретного маршруту використовують наявні WDH-шари.
- Стабільні зелені вузли не змінюються без доведеної регресії.
- Заголовки кешування статичних ресурсів на production є частиною базового стану продуктивності.

### 4.2. Інваріанти картки товару

- Кінцевий порядок DOM у мобільній версії формується на сервері.
- Пізнє переміщення блоків через jQuery не повертається.
- LCP-зображення товару має правильний розмір і високий пріоритет.
- Геометрія product zoom зарезервована до першого відображення.
- `#product-product .product-zoom-image{aspect-ratio:1/1;}` не видаляється без повторної перевірки геометрії.
- Критичний CSS картки товару проходить через `WdhCriticalCss`.
- Поточна стабільна схема залежностей не змінюється ізольовано від залежного коду.

### 4.3. Інваріанти категорії

- Критичний CSS категорії залишається окремим для цього типу сторінки.
- Початкова сітка і геометрія не повинні залежати від пізнього JavaScript-переміщення.
- Пріоритет першого LCP-зображення товару зберігається.
- Критичний CSS не скорочується лише за припущенням «це нижче першого екрана» без фактичної перевірки.
- Поточна пакетна схема відкладеного CSS не замінюється послідовним пізнім завантажувачем.

### 4.4. Інваріанти головної сторінки

- Геометрія Nivo повинна бути правильною **до** ініціалізації slider. На desktop для цього використовується резервування пропорції `1770/617`; на mobile зберігається окремий мобільний інваріант.
- Правило `.common-home.mobile-layout .plaza-slider img{min-height:0;height:auto;}` не видаляється без доведеної регресії.
- Мобільні зображення slider повинні віддаватися у відповідному мобільному розмірі та форматі.
- Nivo на desktop не повинен чекати `window.load`, якщо для ініціалізації достатньо готового DOM; поточний стабільний варіант ініціалізується через DOM ready.
- Старий Swiper lazy не повертається для статичної мобільної сітки `ptproducts`.
- Desktop-карусель `ptproducts` module `206` зберігається, але її важка ініціалізація не повинна входити у critical path першого екрана, якщо модуль знаходиться нижче fold.
- Зображення товарів нижче першого екрана не повинні знову входити в початкове завантаження без причини.
- Приховані форми не дають права їх стороннім залежностям блокувати initial load. Зокрема reCAPTCHA прихованої ajax-реєстрації на desktop homepage завантажується лише після явного кліку `Register`.
- Mobile homepage не змінюється через desktop-оптимізації, якщо її поточний стан уже стабільний.
- Синхронний jQuery на головній сторінці є **відомим стабільним винятком**, а не автоматичною регресією; його не змінювати без повної повторної перевірки залежностей.

## 5. Архітектурна модель WheelDecalsHub

Загальну модель можна представити так:

```text
OpenCart / Plaza
        ↓
WDH OCMOD layer
        ↓
WDH PHP libraries
        ↓
відображення для маршруту та типу пристрою
        ↓
критичні / відкладені ресурси
        ↓
серверні заголовки кешування
        ↓
кеш браузера + відображення сторінки
        ↓
Core Web Vitals
```

Для діагностики діє окрема модель шляху від вихідного коду до браузера:

```text
вихідний файл
→ OCMOD Refresh
→ storage/modification
→ PHP-інтеграція
→ кеш Twig
→ фактичний HTML
→ HTTP-заголовки
→ завантаження ресурсів браузером
→ кінцевий DOM і геометрія
```

Ця модель важлива: зміна може вже бути правильною у вихідному файлі, але ще не проявлятися у браузері через згенерований код або кеш шаблонів.

## 6. Компоненти реалізації

### 6.1. Вихідні файли критичного CSS

Основні файли:

```text
catalog/view/theme/tt_uren1/stylesheet/wdh/critical-common-mobile.css
catalog/view/theme/tt_uren1/stylesheet/wdh/critical-home-mobile.css
catalog/view/theme/tt_uren1/stylesheet/wdh/critical-category-mobile.css
catalog/view/theme/tt_uren1/stylesheet/wdh/critical-product-mobile.css
catalog/view/theme/tt_uren1/stylesheet/wdh/critical-desktop.css
```

Ці файли є єдиним джерелом істини для критичного CSS.

Не повертатися до великих дубльованих блоків CSS усередині OCMOD XML.

### 6.2. `WdhCriticalCss`

PHP-бібліотека:

```text
system/library/wdh/critical_css.php
```

`WdhCriticalCss` збирає критичний CSS для конкретного типу сторінки та пристрою з окремих вихідних CSS-файлів, кешує готовий результат і передає його для вставки у `<head>` як inline `<style>`.

Кеш критичних стилів зберігається окремо у:

```text
DIR_STORAGE . 'cache/wdh_critical_css/'
```

Готовий кеш автоматично перебудовується, якщо один із вихідних CSS-файлів був змінений пізніше за кеш. Завдяки цьому після зміни критичного CSS не потрібно вручну синхронізувати великі inline-блоки.

Під час запису нового кешу використовується тимчасовий файл із подальшим `rename()`, що зменшує ризик отримати частково записаний CSS при паралельних запитах. В окремих аварійних сценаріях бібліотека може повернути останній валідний кеш замість порожнього критичного CSS.

Таким чином, критичні стилі зберігаються у звичайних CSS-файлах як єдиному джерелі істини, а робочий кеш є лише згенерованим шаром і не повинен редагуватися вручну.

Новий критичний CSS для конкретного маршруту повинен підключатися через цю архітектуру, а не окремим випадковим inline-блоком.

Інтегратор:

```text
system/wdh_critical_css_loader.ocmod.xml
```

`WdhCriticalCss` відповідає за:

- читання вихідного CSS;
- складання спільного CSS і CSS для конкретного маршруту в правильному порядку;
- окремі варіанти для mobile і desktop;
- робочий кеш;
- перебудову кешу за `filemtime`;
- безпечний запис через тимчасовий файл і `rename()`;
- повернення останнього валідного кешу в окремих аварійних сценаріях.

### 6.3. Відкладений CSS

Некритичні stylesheets не повинні конкурувати з першим відображенням.

Поточна схема зберігає вилучені з критичного шляху посилання на стилі як:

```html
<template class="wdh-deferred-css">
```

Після `window.load` пакет відкладеного CSS може завантажуватися у фоні, а його застосування відбувається контрольовано після взаємодії користувача.

Інтегратор:

```text
system/wdh_catalog_deferred_assets.ocmod.xml
```

Послідовний відкладений завантажувач CSS, який давав поетапне перемальовування і великий CLS, не повертається.

### 6.4. Визначення mobile

Plaza вибирає мобільне відображення на сервері через `Mobile_Detect`.

У проєкті прийнято:

```text
mobile  = isMobile() && !isTablet()
tablet  = desktop behavior
desktop = desktop behavior
```

Мобільний header:

```text
catalog/view/theme/tt_uren1/template/plaza/page_section/header_mobile.twig
```

Вузьке desktop-вікно не є еквівалентом справжнього mobile-render.

### 6.5. JavaScript-залежності

У проєкті немає правила «jQuery завжди має бути deferred».

Правило інше:

> **Схема роботи залежності є частиною контракту конкретного типу сторінки і змінюється лише разом із кодом, що від неї залежить.**

`wdhWhenJQuery(...)` використовується там, де відкладений jQuery стабільно працює із застарілим залежним кодом.

На головній сторінці синхронний jQuery зараз є свідомим винятком: defer спричинив реальні помилки `$ / jQuery is not defined`, тоді як поточний базовий стан головної вже зелений.

**Google Analytics навмисно виключено з початкового навантаження, яке впливає на PSI.** Це зроблено для того, щоб сторонній аналітичний скрипт не конкурував із критичними ресурсами першого екрана. Змінювати цей порядок без повторної перевірки PSI та Core Web Vitals не слід.

Окреме правило для сторонніх віджетів і прихованих форм:

> **Наявність елемента в DOM не означає, що його важкий сторонній runtime має виконуватися під час initial load.** Якщо функція потрібна лише після явної дії користувача, її залежність завантажується у момент цієї дії, за умови що функціональність після активації повністю зберігається.

Це правило застосовано до Google reCAPTCHA у прихованій формі ajax-реєстрації на desktop homepage.

#### Встановлений OCMOD `WDH Product Autocalc Deferred`

Через адмін-панель OpenCart встановлено власний модифікатор:

```text
WDH Product Autocalc Deferred
code: wdh_product_autocalc_deferred
```

Він адаптує JavaScript картки товару до відкладеного завантаження jQuery: код перерахунку ціни та обробники опцій запускаються через `wdhWhenJQuery(...)` після того, як jQuery стає доступним.

Модифікатор є частиною стабільної архітектури сторінки товару. Його не слід видаляти або замінювати прямими правками згенерованих файлів.

У проєкті одночасно можуть існувати OCMOD, встановлені через адмін-панель, і файлові WDH OCMOD. Під час діагностики конфліктів або змін у згенерованому коді потрібно враховувати обидва джерела модифікацій.

### 6.6. Доставка зображень

Стратегія залежить від ролі ресурсу:

- LCP: раннє виявлення, високий пріоритет, без lazy-load, правильний розмір і формат;
- інші зображення першого екрана: стабільна геометрія і відсутність зайвого oversize;
- нижче першого екрана: lazy-load або завантаження після взаємодії, якщо це не шкодить UX і геометрії;
- адаптивні сценарії: `srcset` / `<picture>` там, де це дає реальний виграш.

Підтримка WebP реалізована в `catalog/model/tool/image.php`. Метод `resizeWebp(...)`, який додається через `system/wdh_image_webp.ocmod.xml`, створює зменшену копію зображення у форматі WebP із заданими розмірами та якістю. Він використовується там, де потрібно віддати браузеру оптимізоване зображення, близьке до фактичного розміру відображення, без зайвих пікселів і ваги. Для LCP-зображень параметри `resizeWebp(...)` підбираються відповідно до фактичної геометрії елемента на сторінці.

### 6.7. Шрифти

Google Fonts прибрано. Основний Work Sans зберігається локально:

```text
catalog/view/theme/tt_uren1/fonts/worksans/WorkSans-v24-latin.woff2
```

Preload у мобільному header має бути після `<base>`, інакше відносний URL на вкладених сторінках може визначитися неправильно.

Окремий невеликий шрифт **Bestin** навмисно вбудовано у вигляді base64 як точкову оптимізацію першого екрана. Це прибирає окремий мережевий запит, прискорює появу правильного шрифту, зменшує ризик пізньої підміни шрифту та пов'язаного з нею CLS, а також допомагає стабільності першого відображення і опосередковано FCP/LCP.

Це рішення застосоване саме до невеликого Bestin і не є загальним правилом для всіх шрифтів. Великі шрифти на кшталт Work Sans не слід автоматично переводити у base64, оскільки це збільшить початковий HTML і може погіршити час його завантаження та розбору.

### 6.8. Критичні іконки

Для елементів першого екрана проєкт не покладається на повний шрифт Ionicons.

Іконки шапки на сторінках сайту реалізовані окремими SVG. На сторінках категорії та товару критичні іконки першого екрана також використовують окремі SVG, щоб їх відображення не вимагало завантаження повного іконкового шрифту.

Окремий виняток — блок `policy-block` на головній сторінці. Для нього було створено зменшену вибірку з Ionicons:

```text
catalog/view/javascript/ionicons/fonts/ionicons-policy.woff2
```

`ionicons-policy.woff2` містить лише ті символи Ionicons, які потрібні для `policy-block`. Це дозволяє не завантажувати повний іконковий шрифт заради кількох іконок цього блоку.

**Інваріант:** не повертати повний Ionicons у критичний шлях першого відображення. Для шапки, категорії та сторінки товару зберігати SVG-підхід, а для `policy-block` — поточний `ionicons-policy.woff2`, доки немає обґрунтованої причини змінювати цю схему.

### 6.9. Дані Plaza, що зберігаються в БД

Частина головної сторінки зберігається не у Twig-файлах, а в `oc_module`.

Підтверджені приклади:

```text
module_id 196 — Static1 Store1 — ptstaticblock
module_id 45  — Payment       — ptstaticblock
```

Тому перевірка джерел головної сторінки повинна враховувати стан БД/адмінки, а не лише Git-репозиторій.

3. залишити решту стилів компонента відкладеними;
4. перевірити початкову геометрію та CLS;
5. перевірити стан після підключення відкладеного CSS.

## 8. Зміни та доробки CSS

Перед будь-якою CSS-зміною потрібно визначити, до якого шару вона належить:

```text
critical / deferred
+
route-specific / common
```

### 8.1. Правила

- Не переносити правило в критичний CSS лише тому, що без нього «щось виглядає не так».
- У критичному шарі залишаються лише стилі, потрібні для першого відображення, стабільної геометрії та запобігання CLS.
- Не дублювати одне правило у кількох критичних файлах без архітектурної потреби.
- Правило для конкретного маршруту не переноситься у спільний файл лише для зручності.
- Не повертати великий stylesheet у блокувальний `<head>` заради локального виправлення.
- Якщо з відкладеного CSS для першого відображення потрібна лише частина блоку — у критичний CSS додається мінімально необхідний набір правил, а не весь блок.
- Не створювати друге джерело істини.
- Будь-яка зміна макета першого екрана вважається чутливою до продуктивності.
- CSS, що визначає геометрію JavaScript-компонента, має бути правильним **до його ініціалізації**.

### 8.2. Особливо чутливі CSS-властивості

Особливо уважно змінювати:

- `display`;
- `position`;
- `width` / `height` / `min-height`;
- `margin` / `padding`;
- `font-size`;
- `line-height`;
- `aspect-ratio`;
- розміри зображень і контейнерів;
- розміри slider/carousel;
- sticky/fixed-блоки;
- pseudo-elements, що впливають на геометрію;
- media queries для mobile/tablet/desktop.

Після таких змін перевіряється не лише кінцевий вигляд, а й:

```text
початкова геометрія
→ геометрія після підключення відкладеного CSS
→ зміщення макета
→ LCP / CLS
```

### 8.3. Нові компоненти першого екрана

> **Нова функціональність першого екрана не повинна змушувати повертати весь stylesheet у блокувальний режим. Для неї додається мінімальний критичний набір правил, а решта стилів залишається відкладеною.**

## 9. Нові OCMOD-модифікатори: правила інтеграції

Новий OCMOD не розглядається як ізольований модуль. Перед впровадженням перевіряється його вплив на поточну архітектуру продуктивності.

### 9.1. Що перевірити до встановлення або адаптації

Чи не робить модифікатор наступне:

- повертає блокувальні CSS/JS у `<head>`;
- додає новий синхронний jQuery;
- вставляє великі inline-блоки CSS/JS;
- змінює DOM першого екрана після першого відображення;
- підміняє `header.twig` / `header_mobile.twig` так, що обходить `WdhCriticalCss`;
- використовує ті самі OCMOD-якорі, що й WDH-шар;
- додає зображення без стабільної геометрії або відповідної стратегії завантаження;
- створює другий механізм визначення mobile;
- створює паралельний завантажувач critical/deferred CSS;
- примусово вставляє залежності у `<head>` в обхід наявної схеми.

### 9.2. OCMOD-якорі — частина контракту

Перед видаленням або суттєвою зміною рядка вихідного коду потрібно перевірити, чи не використовується він як `<search>`-якір іншого OCMOD.

У цьому проєкті вже була регресія, коли видалення застарілих рядків переміщення product DOM одночасно зламало WDH OCMOD-wrapper і дало:

```text
Uncaught ReferenceError: $ is not defined
```

Для WDH OCMOD у цьому середовищі не покладатися на багаторядкові `<search>`-якорі. Використовувати унікальний однорядковий якір + `position` / `offset`.

### 9.3. Головне правило інтеграції

> **Якщо сторонній OCMOD конфліктує з інваріантами продуктивності проєкту, адаптується новий OCMOD, а не вимикається стабільна архітектура оптимізації.**

Не можна вирішувати конфлікт глобальним поверненням застарілої блокувальної поведінки.

### 9.4. Перевірка після OCMOD

```text
зміни вихідного коду
→ OCMOD Refresh
→ згенеровані файли
→ фактичний HTML
→ Console
→ Network
→ DOM / геометричні інваріанти
→ репрезентативний запуск PSI
```

`storage/modification` не редагується як джерело постійних змін.

Важливий факт для цього проєкту: стандартний Refresh у `admin/controller/marketplace/modification.php` читає не лише записи з таблиці модифікацій, а й усі файли:

```php
glob(DIR_SYSTEM . '*.ocmod.xml')
```

Тому WDH-файли `system/*.ocmod.xml` є активними source-файлами модифікацій і можуть застосовуватися без окремого запису в `oc_modification`. Не робити висновок про неактивність файлового OCMOD лише через відсутність його в SQL-дампі.

Так само не можна вгадувати фізичний шлях `storage/modification` на hosting. Потрібно перевіряти фактичний `DIR_STORAGE` / знайдений production-файл, а вже потім аналізувати згенерований код.

## 10. Кешування статичних ресурсів на production-хостингу

> **Серверні заголовки кешування є частиною архітектури продуктивності WheelDecalsHub і поточного базового стану PSI.**

На production уже налаштовано тривале кешування статичних ресурсів у браузері.

Підтверджений приклад для Work Sans:

```text
Cache-Control: max-age=31622400
Expires: ~1 year
Content-Type: font/woff2
Content-Length: 50524
```

Ця політика повинна охоплювати відповідні типи статики — шрифти, CSS, JS та зображення — відповідно до фактичної конфігурації сервера.

### 10.1. Контракт production-середовища

- Не скорочувати TTL статичних ресурсів випадково.
- При перенесенні сайту на інший hosting відтворити еквівалентні заголовки кешування.
- Базовий стан продуктивності не вважається відтвореним після перенесення, доки політика кешування статики не перевірена фактичними HTTP-заголовками.
- При повторних запитах статики перевіряти заголовки відповіді, а не лише HTML.

### 10.2. Де налаштовано кешування

Кешування статичних ресурсів і GZip-стиснення налаштовані на рівні хостингу через панель керування **ISPmanager**.

Шлях у панелі:

```text
ISPmanager
→ WWW-домени / Сайти
→ вибрати wheeldecalshub.com
→ Змінити
→ Налаштування оптимізації сайту
```

У цьому розділі задаються:

- GZip-стиснення;
- строк дії кешування статичних ресурсів.

Після збереження ISPmanager автоматично переконфігурує веб-сервер.

Ці налаштування є частиною поточного базового стану продуктивності. При перенесенні сайту на інший хостинг або зміні конфігурації веб-сервера їх потрібно відтворити та перевірити за фактичними HTTP-заголовками.

#### Desktop homepage — стабільний зелений стан 2026-10-14

Після окремої desktop-діагностики головна сторінка також доведена до зеленого стану. Репрезентативний контрольний PSI після виправлення reCAPTCHA:

```text
Performance: 97
FCP: 0.7 s
LCP: 1.1 s
TBT: 50 ms
Speed Index: 1.2 s
CLS: 0.001
```

Це поточний desktop baseline. Не «дооптимізовувати» його без конкретної відтворюваної причини.

##### Desktop Nivo geometry / CLS

Початковий desktop CLS близько `0.227` був пов'язаний з тим, що slider не резервував висоту до появи `.nivo-main-image`. Layout shift переміщував `.main-row`.

Для homepage створено окреме джерело критичного CSS:

```text
catalog/view/theme/tt_uren1/stylesheet/wdh/critical-home-desktop.css
```

Ключове правило:

```css
.common-home .plaza-slider{aspect-ratio:1770/617;}
```

`WdhCriticalCss::buildDesktop()` тепер має окрему гілку `common/home`, яка формує кеш:

```text
home-desktop.css
```

Після резервування геометрії CLS стабільно знизився приблизно до `0.001–0.003`.

##### Desktop Nivo init / LCP

У `catalog/view/theme/tt_uren1/template/plaza/module/ptslider.twig` ініціалізацію Nivo перенесено з:

```javascript
$(window).load(function() { ... })
```

на DOM ready:

```javascript
$(function() { ... })
```

Причина: перше slider-зображення вже виявлялося браузером рано, але створення `.nivo-main-image` чекало `window.load`. Після зміни LCP покращився приблизно з `2.0–2.4 s` до `1.5–1.6 s`, а після наступних оптимізацій у репрезентативному PSI до `1.1 s`.

Важливо: Nivo змінює `src` одного й того самого `.nivo-main-image` під час циклу слайдів. Тому Lighthouse може показувати URL пізнішого banner як «LCP element» і давати внутрішньо суперечливий breakdown. Для причинного аналізу перевіряти Resource Timing / Performance trace, а не довіряти лише поточному `src` цього DOM-вузла.

##### Desktop `ptproducts` module 206 / TBT

На desktop module `206` залишається справжньою Swiper-каруселлю. Її не перетворювати на статичну mobile-схему.

Оскільки блок знаходиться нижче першого viewport, ініціалізація Swiper відкладена через `IntersectionObserver` з near-viewport порогом:

```text
rootMargin: 200px 0px
```

При вході блоку у зону спостереження observer відключається і виконується початкова конфігурація Swiper без зміни її параметрів. Fallback без `IntersectionObserver` виконує звичайну ініціалізацію.

Ця зміна зменшила desktop TBT у PSI приблизно з `320–340 ms` до близько `220 ms`, не погіршивши LCP/CLS.

##### Ajax register / reCAPTCHA — lazy лише для desktop homepage

Plaza-модуль `ptajaxlogin` безумовно будує приховану форму реєстрації при initial render:

```text
catalog/controller/extension/module/ptajaxlogin.php
  → $this->load->controller('plaza/register')
```

`plaza/register::index()` підключає стандартну captcha, а стандартний шаблон captcha містить Google API script. У результаті прихована `#ajax-register-form` з `height:0` змушувала reCAPTCHA виконуватися ще до кліку користувача.

PSI показав, що до виправлення **7 із 8 long tasks** походили від Google reCAPTCHA (`recaptcha__*.js`), тоді як власний Swiper був лише однією з восьми задач.

Рішення навмисно вузьке:

1. У `catalog/controller/extension/captcha/google.php` передається прапорець `wdh_desktop_home`.
2. Визначення пристрою використовує наявний `Mobile_Detect`; tablet залишається в desktop-поведінці.
3. Для homepage без явного `?route=` fallback маршруту має бути `common/home`, інакше прапорець помилково буде false на `/`.
4. `system/wdh_product_recaptcha_lazy.ocmod.xml` зберігає стару product-логіку і має окрему гілку `wdh_desktop_home`.
5. На desktop homepage Google reCAPTCHA API не завантажується під час initial load; він додається лише після кліку `#pt-register-link`.
6. На mobile homepage поведінка captcha не змінюється.
7. Інші сторінки використовують стандартний fallback і не змінюються.

Функціональна перевірка:

```text
до кліку Register: resource list recaptcha/gstatic = []
після кліку Register: Google reCAPTCHA resources завантажуються, captcha і форма працюють
```

Після цього TBT у репрезентативному desktop PSI знизився до `50 ms`, а reCAPTCHA повністю зникла зі списку initial long tasks.

##### Виняток для jQuery на головній сторінці

На головній сторінці jQuery зараз завантажується синхронно.

Було протестовано defer, але він спричинив реальні помилки `$ / jQuery is not defined`.

За поточного desktop стану `Performance 97 / TBT 50 ms` і стабільного mobile baseline це не вважається проблемою, яку потрібно «дооптимізувати» без окремого доказу.

## 14. Відомі винятки та небезпечні зони

### 14.1. Відомі винятки

- Google Analytics навмисно виключено з початкового навантаження, яке впливає на PSI, щоб сторонній аналітичний скрипт не конкурував із критичними ресурсами першого екрана.
- Синхронний jQuery на головній сторінці — свідомий стабільний виняток після невдалого defer-експерименту.
- Частина вихідних даних головної сторінки зберігається у `oc_module`, а не у файлах репозиторію.
- Tablet навмисно використовує desktop-поведінку.
- Ajax-register форму Plaza можна рендерити приховано на initial load, але її Google reCAPTCHA на desktop homepage навмисно завантажується лише після кліку `Register`.
- Файлові OCMOD у `DIR_SYSTEM/*.ocmod.xml` читаються стандартним Refresh напряму; відсутність запису в `oc_modification` не означає, що модифікація неактивна.

### 14.2. Не повторювати без нового доказу

1. Послідовне відкладене завантаження CSS — давало поетапне перемальовування і великий CLS.
2. Переміщення mobile product DOM на боці клієнта після першого відображення.
3. `width/height` головного product image через стару `thumb_dimension`-логіку — ламало геометрію Cloud Zoom.
4. Defer jQuery на головній сторінці як ізольована зміна — дав race conditions.
5. Старий Swiper lazy для статичної мобільної сітки товарів.
6. `width/height` на трьох статичних промозображеннях без перевірки геометрії — давало вертикальне розтягування.
7. Великі дубльовані inline-блоки критичного CSS усередині OCMOD.
8. Правки `storage/modification` або робочого кешу як джерела постійних змін.
9. Масове «прибирання» вже стабільних product/category/homepage без доведеної регресії.
10. Відключення всієї прихованої ajax-register форми лише заради PSI, якщо достатньо відкласти її важку сторонню залежність reCAPTCHA.
11. Перенесення desktop-only оптимізації reCAPTCHA на mobile homepage без окремого доказу потреби.

## 15. Вимоги до перевірки після змін

Будь-яка доробка, що впливає на продуктивність, не вважається завершеною лише тому, що «візуально працює».

Мінімальна послідовність перевірки:

```text
зміна вихідного коду / БД
→ потрібний OCMOD Refresh або Theme Refresh
→ згенерований стан
→ фактичний HTML
→ Console
→ Network
→ DOM + геометричні інваріанти
→ репрезентативний запуск PSI
```

Залежно від типу зміни додатково перевіряти:

- LCP-елемент і час його запиту;
- природні та фактичні розміри зображень;
- `fetchpriority` і lazy-load;
- зміщення макета;
- запити шрифтів;
- геометрію до та після підключення відкладеного CSS;
- mobile UA проти вузького desktop-вікна;
- заголовки кешування статичних ресурсів.
- для lazy third-party залежностей — відсутність їхніх Network/Resource Timing запитів до тригера та повну працездатність після тригера;
- для файлових OCMOD — фактичний згенерований файл у production `DIR_STORAGE`, а не припущений локальний шлях.

Один аномальний запуск PSI не є достатнім доказом регресії.

## 17. Короткий контракт для майбутнього розробника

Перед будь-якою суттєвою доробкою потрібно відповісти на п'ять питань:

1. **Чи потрібен цей ресурс першому екрану?** Якщо ні — він не повинен без причини блокувати відображення.
2. **Чи знає браузер кінцеву геометрію до першого відображення?** Якщо ні — є ризик CLS.
3. **Чи змінюється залежність разом із кодом, що від неї залежить?** Якщо ні — є ризик race conditions або помилок виконання.
4. **Чи використовується наявний WDH-шар, а не створюється паралельний механізм?**
5. **Чи залишилися стабільними метрики сторінки і функціональність після зміни?**
